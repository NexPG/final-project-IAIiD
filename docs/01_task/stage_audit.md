## 2. Этап 2. Архитектура

### Что есть

- бизнес-контекст и ожидаемый эффект;
- синхронный сервис;
- компоненты: приложение, backend, сервис классификации, очереди;
- поток данных;
- 7 классов;
- контракт `POST /api/v1/classify` с `text`, `user_id`, `class`, `confidence`, `queue`, `model_version`;
- ограничения: только текст, низкая уверенность → manual, нет drift/переобучения, версия модели есть, но управление версиями неполное.

### Чего не хватает по вебинарам В02–В03

- сравнения монолит vs микросервисы;
- обоснования batch vs stream;
- паттерна интеграции model-as-a-service vs embedded;
- сравнения classical ML vs LLM/agent;
- трёх узких мест с последствиями отказа;
- SLA и поведения при ошибках;
- семантического версионирования API/модели/данных;
- hidden dependencies и feature store;
- наблюдаемости;
- связи с 7 этапами ЖЦ;
- ролей и рисков по этапам.

### Решение

Переписать `docs/02_architecture/architecture.md` и `docs/02_architecture/api.md` по TZ §7–§8. Сохранить 7 классов и общий поток, но добавить обоснования, ADR, SLA, версионирование и 3 узких места. Старый отчёт использовать только как черновик.

## 3. Этап 3. Эксперименты

### Что есть

- 420 синтетических обращений, 7 классов, по 60 на класс;
- 140 сценариев × 3 формулировки;
- split 252/84/84 по сценариям, seed 42;
- 6 MLflow runs: keyword baseline + 5 моделей TF-IDF/LogReg;
- лучший результат: word+char, C=4, macro-F1 0.929 на test (84 примера);
- Great Expectations: 13 expectations, 14 pandas-правил;
- намеренно испорченная копия данных, 12 нарушений;
- 44 программных теста;
- 6 model tests, 4 прошли, 2 нашли ограничения;
- найден баг: «Подписку отменять не хочу, нужен чек об оплате» → `subscription`, ожидается `payment`;
- threshold 0.0 на validation, automation disabled;
- confidence не калиброван;
- test 84, по 12 на класс;
- модель `artifacts/model.joblib`, MLflow, ноутбук, отчёты.

### Сильные стороны

- честно указано, что данные синтетические;
- MLflow используется правильно: params, metrics, model, confusion matrix, hashes;
- data validation с dirty copy;
- group split по сценариям;
- найден и описан реальный баг;
- automation отключена, а не замаскирована;
- есть bootstrap-интервал;
- есть README и воспроизводимость.

### Чего не хватает

- test 84 — мало, 12 на класс;
- нет human-verified test/validation;
- нет `channel`/`locale`;
- нет калибровки;
- threshold 0.0 — не работает как abstention;
- automation disabled — нет бизнес-эффекта;
- нет transformer-сравнения (опционально);
- API только один эндпоинт, нет healthcheck/model-info/request_id;
- нет integration с очередью;
- нет load test;
- нет PII-тестов;
- `.github/workflows` не используем.

### Решение

Использовать как **baseline и seed**:

- сохранить 7 классов и сценарии;
- провести аудит 420;
- добавить реальный домен TWCS SpotifyCares и вспомогательный Bitext;
- train — 8 000 минимум, цель 15 000–20 000; слабые метки только train;
- заменить старый test на 80/20 frozen test; validation заменить на StratifiedGroupKFold CV;
- повторить E0–E4 на новом split;
- откалибровать и подобрать threshold/margin;
- пересчитать метрики;
- добавить `channel`/`locale`, `label_quality` и PII-кейсы;
- переписать API под TZ §8;
- старые метрики 0.929 не выдавать за финальные.

## 4. Этап 4. Тестирование

### Что есть

- 9 проверок в тест-плане;
- 44 code tests;
- 6 model tests: macro-F1, recall, uppercase, spaces, typo, empty, too long, routing, negation;
- найден баг с отрицанием;
- TestClient и mock-модель;
- тест на 503 при сбое модели;
- JUnit/логи.

### Чего не хватает

- contract test против OpenAPI;
- PII-тест;
- subgroup test по каналу/языку/длине;
- adversarial test;
- load test;
- feedback idempotency;
- batch order;
- model-info/healthcheck;
- request_id;
- проверка, что `needs_human_review` работает по margin, а не только threshold;
- E2E с реальной очередью (можно описать как out of scope).

### Решение

Сохранить идеи и найденный баг, переписать тесты под новый API и routing. Добавить недостающие уровни. Найденный баг с отрицанием использовать как обязательный кейс в отчёте.

## 8. Итог

Текущий черновик этапов 2–4 — хорошая заготовка, но **не финальный проект**. Особенно полезны:

- 7 классов и сценарии;
- MLflow-подход;
- data validation;
- найденный баг с отрицанием;
- честное описание ограничений.

**Обновление по данным:** старый план «собрать 1 050–1 200 вручную» заменён. Для NLP-проекта этого мало, а готового русского домена нет. Финальная стратегия — объединённый пул TWCS + Bitext, 80/20 stratified split, CV на train и один frozen test. Это даёт 10 713 train и 2 714 test.

Всё остальное приводим к TZ и вебинарам.
